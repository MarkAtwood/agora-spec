# Review 3 verification: CRY3

Verified against the working tree on 2026-10-17. Binding decisions checked: `agora-dm-removal`, `agora-d2-sequencer`, `agora-doorkey-B`, `agora-broadcast-decision`, `agora-format-open`.

### CRY3-1: Stamped-Commit "counts" rule forks catch-up members; the 10 s check uses a sender-chosen timestamp
- Verdict: CONFIRMED. spec/05-messaging.md:31 and :34 read as quoted. §11.4 (spec/11-transport.md:184) admits any envelope whose `ts` is not more than 300 s ahead and not older than `retentionDays`, so a late publish with `ts` = stamp `ts` passes criterion 1 at every Relay and in history. The 15 s hold is local arrival time. The withhold-then-publish attack works as described. spec/14-jmap.md (§14.4.3, last paragraph of distribution) repeats the window: "For a commit stream, such a copy counts only within the publication window of §5.1.1." Same defect as IMP3-1.
- Severity: P1, keep. Any member with commit rights can split the group at will, and honest relay delay of more than about 5 s splits it by accident.
- Fix (shared with IMP3-1, option (a)). The log already stores (stamp, `op`) and `op` is the exact `sealedEnvelope`, so the winner can be read from the log alone.
  1. spec/05-messaging.md §5.1.1, replace the "counts" paragraph, items 1 and 2, and the following paragraph with: "A stamped Commit **counts** if it opens under the epoch's sealing key (§5.2.2), decrypts, and is a well-formed Commit for that epoch that passes RFC 9420 §12.4.2 validation and the checks of §5.2.1. The winning Commit for epoch N is the counting Commit for epoch N at the lowest position of the commit stream, taken from the sequencer log (§14.4.3), whether or not it was ever published. A member that receives a stamped Commit for epoch N at position p, or whose committer's own submission returned position p, fetches the commit stream log up to p before applying anything for epoch N, and applies the winning Commit it finds there. If the log is unreachable the member waits. A member that applies a winning Commit it has not received in a routing envelope publishes it, in a routing envelope for the stream's `channelToken` whose `sealedEnvelope` is the logged `op` and whose `commitStamp` is the logged stamp, so that history holds every winning Commit. A member that sees a stamped Commit fail to count treats its sender as misbehaving, as for any message that fails MLS processing."
  2. Same paragraph: delete "unless a Commit at an earlier position already counts" from the committer sentence and replace with "unless the log up to its own position already holds a counting Commit for the epoch, in which case its Commit has lost."
  3. spec/14-jmap.md §14.4.3: delete "For a commit stream, such a copy counts only within the publication window of §5.1.1."
  4. Grep for "15 seconds" and "Published in time" and remove remaining references (Appendix limits table if listed).
- Needs decision: yes. (a) Winner from the log alone, losers never matter, the first member to apply an unpublished winner republishes it (recommended). (b) Relays parse `commitStamp` and refuse an envelope whose stamp `ts` is more than 10 s behind their clock; keeps clocks and the 15 s hold, so online members still diverge on arrival. (c) Keep the text and document that catch-up members can fork. Plain language: today two members can disagree about which of two competing changes won, depending on when each one came online, and once they disagree they can no longer read each other. Option (a) makes the sequencer's numbered list the only referee, so everyone who reads the list picks the same winner.

### CRY3-2: "Valid" criterion depends on each member's current Space state
- Verdict: CONFIRMED problem, PARTIAL fix. spec/05-messaging.md:32 reads "authorized for every change it makes under current Space state (§4)"; Space state heads differ between members while a new state propagates (§5.1.1 "Space state ordering" shows heads can even fork). The reviewer's fix says an authorization failure is "handled by a later Commit", which misstates §4.5: spec/04-access-control.md:141 says a client receiving a policy-violating Commit "MUST NOT process later messages in that group ... and MUST leave the group". Residual: §5.2.1 leaf checks use the DID's "current DID document" (spec/05-messaging.md, Authentication Service paragraph), which also differs between members during a DID update; out of scope here, noted only.
- Severity: P2, keep.
- Fix: in the CRY3-1 replacement text, "counts" already omits the Space state clause. Add to §5.1.1 after it: "Whether a Commit is authorized under Space state (§4) does not affect which Commit wins. A member that finds the winning Commit unauthorized under the Space state head it holds first fetches the current head from the Space endpoint (§3.4) and re-checks; if the Commit is still unauthorized, it treats it as a policy violation (§4.5)." This keeps the MLS outcome identical for every member; only the leave decision can still depend on a member's state view, and the refetch narrows that to a real violation.
- Needs decision: yes. (a) Winner by MLS validity only, authorization checked afterwards as a policy violation with a head refetch (recommended). (b) Committer names the Space state CID it relied on in the Commit's `authenticated_data`, members check authorization against that state if it is on the winning chain and is the head or was the head within a bound; deterministic but adds a field and a staleness rule. Plain language: members can briefly disagree about who is an admin, and today that disagreement decides which change the group accepts, which splits the group. With (a) the group always agrees on the change, and a member who later confirms it was not allowed reacts as it would to any rule break.

### CRY3-3: Commits on the new token only, so members that have not refetched the key miss them for up to the grace period
- Verdict: CONFIRMED. spec/05-messaging.md:27 and spec/10-relays.md:854 and :878 close the old commit stream at registration of the rotated key. Member duties (spec/05-messaging.md, Member duties bullet) trigger a key fetch on reconnect, on a removal Commit, on `token-withdrawn`, and hourly; nothing fires on a periodic or compromise rotation the member did not cause. `token-withdrawn` arrives only at deregistration (grace RECOMMENDED 300 s). Previous sealing key retained 60 s (spec/99-appendices.md:95). Correction to the evidence: application messages from members who already fetched the new key were also on the new token before this delta, so a stale member was already deaf to them; the regression is limited to Commits, but the fix closes both.
- Severity: P2, keep.
- Fix: spec/11-transport.md §11.4 "Withdrawn tokens": add "When a Relay applies a registration whose key has `replaces` (§10.5.3), it sends each connection subscribed to the replaced token an `Error` without `id`, with code `token-rotated` and `token` set to the replaced token, and keeps those subscriptions open. On `token-rotated` the client fetches the current `ChannelAdmissionKey` (§5.2.2)." Add `token-rotated` to the error code list (spec/11-transport.md:137) and to the "exceptions ... which concern one token and leave the connection open" sentence (:191). spec/10-relays.md:854: replace "Other IOs ignore `replaces`." with "A Relay uses `replaces` only to send `token-rotated` (§11.4)." Add "when a relay reports `token-rotated`" to the fetch triggers in §5.2.2 Member duties. No new linkage: §10.5.3 already says the IO can link the epochs.
- Needs decision: no

### CRY3-4: DMMembers has no read path, no defined `seq`, and no ordering against MLS Commits, so the host list and the group diverge
- Verdict: CONFIRMED, all five parts. spec/04-access-control.md:166-168 has no members GET; :193 defines `seq` only as "an unsigned integer"; :193-198 classify by pure Addition or pure Removal against the host's current list, so out-of-order PUTs get `403`; :196 orders the addition PUT before the Welcome but nothing orders any PUT after the Commit has won (the Welcome rule at spec/05-messaging.md:37 covers only the Welcome); :196 lets an Addition put any DID in `complianceLoggers`, and :199 makes such an entry unremovable. Overlaps IMP3-5; IMP3-5's GET plus re-read-and-retry is compatible with option (a) below.
- Severity: P2, keep.
- Fix (compatible with IMP3-5):
  1. :193 after "`seq` is an unsigned integer": "equal to the MLS epoch in which the listed membership takes effect."
  2. Replace the acceptance sentence and items 2 and 3 with: "The host accepts a `DMMembers` if its signature verifies, its `ts` is within 300 seconds of the host's clock, its `seq` is greater than that of the current list, it keeps every `complianceLoggers` entry of the current list, and it is a creation (item 1) or is signed by a DID on the current list. A list equal to the current list is answered `204` without change." Keep item 1 (Creation). Keep the duties as a paragraph: "A committer sends the list only after its Commit has won (§5.1.1). The committer of a Commit that adds a DID not already on the list MUST receive a `204` before it delivers the Welcome. The committer of a Commit that removes the last leaf of a DID MUST send the list; a leaver sends a list without its own DID (§4.8). On `409` or `403` the client fetches the current list, recomputes the list from its MLS membership, and retries." "The host rotates the key when it accepts a list that removes a DID."
  3. Add `GET <host>/admission-key/<groupID>/members → current DMMembers` to the API block, served to authenticated listed DIDs.
  4. Add to §12 (security considerations): "An identity host cannot verify that a DID added to `complianceLoggers` is a logger. A member can thereby give any DID a permanent place on the host's list, which yields the admission key (the ability to post envelopes that fail MLS processing) but no content."
  Residual noted, not fixed: a listed member can PUT a very large `seq` and freeze the list; this is within the power the binding decision already gives (any listed DID may remove every other DID).
- Needs decision: yes. (a) `seq` = MLS epoch, any later list from a listed DID that keeps the loggers, PUT only after win, add GET (recommended). (b) Keep the pure-addition/pure-removal classification, add GET, retry on `409`/`403`; out-of-order delivery still fails. Plain language: the server that hands out the group's door key keeps its own copy of who is in the group, and today members cannot read that copy or tell it which group change came first, so the copy drifts from reality. Option (a) numbers each copy by the group's own change counter and lets members read it.

### CRY3-5: A removal at the host that has no matching MLS removal strands the remaining members with no recovery
- Verdict: CONFIRMED. spec/04-access-control.md:197 allows one removal PUT to drop "one or more DIDs" signed by any listed DID; :271 forbids moving the host while the host's user is a member; :278 lets the host stop serving only after 30 days. Locked-out members can publish only on the old token until deregistration. Adversarial note on the reviewer's option (a): "the current host refuses a member" is visible only to that member, so other members cannot check it, and the policy-violation rule cannot be applied to it. Option (a) therefore lets any member move the host at will, the same as option (b), with an unenforceable condition attached.
- Severity: P2, keep.
- Fix (option (b)): spec/04-access-control.md §4.6.4, delete "Members MUST treat a Commit that changes `agora_admission_host` while the host's user is still a member as a policy violation (§4.5)." and add: "Any member other than a compliance logger or recorder MAY move the group to its own identity host at any time by steps 1 and 2; members MUST NOT treat such a Commit as a policy violation (§4.5). A member that its admission host refuses (`403`) while it is still in the MLS group SHOULD do so, publishing the Commit under the last admitted key it holds before that key is deregistered." This gives no member more power than the binding decision `agora-dm-removal` already gives (any listed DID may remove every other DID at the host). It also removes the need for CRY3-6's authentication rule.
- Needs decision: yes. (a) Move allowed when the host refuses a member (unenforceable, behaves as (b)). (b) Any member may move the host at any time (recommended; matches "no member has authority over the rest", spec/04-access-control.md §4.6.2). (c) Accept the lockout and document it in §12. Plain language: one member of a direct-message group can tell the key server to drop everyone else, and today the others have no way back in. Option (b) lets any of them move the group to a key server of their own, which the decision that any member may remove any other already implies.

### CRY3-6: `admissionHostDID` is not authenticated, so the host's-user check can be steered
- Verdict: CONFIRMED. spec/04-access-control.md:264 defines the host's user from the descriptor; :217 says the descriptor is authenticated only by the sender's MLS signature, and no rule limits who may send one or what `admissionHostDID` may say. `createdBy` has the same weakness. The reviewer's "derive from GroupContext history" does not work for Welcome joiners, who see no history.
- Severity: P2 if CRY3-5 option (c) is chosen; P3 if CRY3-5 option (b) is chosen, because the host's user then only triggers the automatic handover and a wrong value causes at most an unneeded move.
- Fix: put the DID in the GroupContext, which every member agrees on and every joiner receives. spec/04-access-control.md §4.6, extension paragraph: "whose data is the UTF-8 URL, a line feed (0x0A), and the UTF-8 DID of the host's user". §4.6.4: define the host's user as "the DID in the `agora_admission_host` extension"; delete the `admissionHostDID` field and "absent, it means `createdBy`"; in step 2 set the extension to the new URL and the committer's DID. Add: "Members MUST treat a Commit that sets `agora_admission_host` with a DID other than the committer's (its leaf credential identity) as a policy violation (§4.5)." Remove `admissionHostDID` from the descriptor schema text (:217) and Appendix entries. Format change is allowed (`agora-format-open`).
- Needs decision: no

### CRY3-7: Handover fails when the next member is served by the same identity host, and a creation can be squatted
- Verdict: CONFIRMED. spec/04-access-control.md:195 accepts a creation only as "the first list the host accepts for an `mlsGroupID`"; §4.6.4 step 1 always sends a creation; no branch handles a target equal to the current host. The squat needs the attacker to share an identity host with a remaining member and to know the group ID (a former member).
- Severity: P2, keep (the same-host case is the normal enterprise case and loops every 24 h).
- Fix: §4.6.4, before step 1: "If the member's own identity host is the current host, it skips step 1 and in step 2 changes only the DID in `agora_admission_host` (CRY3-6)." After step 2: "If its host refuses the creation, the member with the next lowest leaf index does the handover." Add to §12: "A former member that shares an identity host with a remaining member can create a list for the group there first, which makes handover skip that host."
- Needs decision: yes. (a) Host-level host's user: handover only when no remaining non-logger member is served by the current host. Removes the case but needs every member to resolve each member's `KeyPackageEndpoint` to judge a policy violation. (b) Same-host shortcut plus next-member fallback, as above (recommended; local, and with CRY3-5 (b) there is no violation to judge). Plain language: when the person whose server holds the group's key leaves, the group moves to the next person's server, and in a company that is often the same server, which today makes the move fail forever. Option (b) says "if it is the same server, just record the new owner and carry on".

### CRY3-8: "One file per key" is ambiguous for revisions and retries, and with index nonces any reuse breaks GCM
- Verdict: CONFIRMED. spec/14-jmap.md:130 reads as quoted; "file" is undefined for a `FileNode` whose content is replaced or an upload re-encrypted after the source changed. Nonce = chunk index makes any reuse a two-time pad plus GHASH key recovery.
- Severity: P2, keep (low likelihood, total loss of confidentiality and integrity for that key).
- Fix: spec/14-jmap.md:130, replace "A client MUST NOT use a `contentKey` for more than one file. Because a key seals exactly one file, the nonce can be the chunk index." with "A `contentKey` seals exactly one plaintext. A client MUST NOT seal two different chunk plaintexts under the same `contentKey` and chunk index; any change of content, including a new revision of the same `FileNode`, uses a fresh `contentKey`. A client that re-encrypts after an interruption uses a fresh key or encrypts from a snapshot it has checked to be unchanged. Because a key seals exactly one plaintext, the nonce can be the chunk index."
- Needs decision: no

### CRY3-9: `prev` = null on a new commit stream when the replaced stream is empty breaks the fork-detection chain
- Verdict: CONFIRMED. spec/14-jmap.md:170 and the stamp schema comment (§14.4.2) use `null` when the replaced stream has no stamps; with T1 to T2 to T3 and T2 empty, T1's last stamp is referenced by nothing. The committer rule in spec/05-messaging.md:27 ("fetches the replaced commit stream to its end") has the same gap.
- Severity: P3, keep.
- Fix: spec/14-jmap.md:170, replace "the hash of the last stamp of the closed commit stream, or `null` if that stream has no stamps" with "the hash of the last stamp of the most recently closed commit stream of the channel that has stamps, or `null` if no earlier commit stream of the channel has stamps"; same wording in the stamp schema comment and the sentence after it. spec/05-messaging.md:27: "fetches the replaced commit stream" becomes "fetches, to its end, the most recently closed commit stream that has stamps".
- Needs decision: no

### CRY3-10: Broadcast poster checks against "current"/"newest" state make past posts undisplayable
- Verdict: CONFIRMED. spec/05-messaging.md:209 ("under current Space state") and :211 ("newest `broadcasters` list it holds"). Removing a poster always rotates `keyEpoch` (:215), so the post's `keyEpoch` identifies the authorization period. A non-member cannot map a view to a `keyEpoch` today, since `broadcasters` entries carry none.
- Severity: P3, keep.
- Fix: :209, "under current Space state" becomes "under the Space state in force while the post's `keyEpoch` was current". :211, add `keyEpoch` to each entry (`{channelID, keyEpoch, dids}`, the channel's current key epoch when the view is issued; update spec/03-spaces.md:233 and spec/99-appendices.md:140), and replace the last sentence with "A non-member subscriber MUST NOT display a post whose `senderDID` is not listed for the channel in a `broadcasters` entry with the post's `keyEpoch`, or, if it holds none for that `keyEpoch`, in the newest list it holds."
- Needs decision: no

- Severity: P3, keep.
- Fix: spec/10-relays.md §10.4.4 eager replication bullet: "with `POST /v1/agora/peer/blob`, carrying the `Agora-Storage-Auth` value of the original upload in the same header". Replicated-blob bullet: after "verifies it against its CID" add "verifies the forwarded `Agora-Storage-Auth` as for an upload (§11.8.2), including `expires` and its own `nonce` replay set". Add: "A Relay that cannot complete eager replication before `expires` stops; pull-through (above) covers the rest." Add the header and a `403` response to the peer POST definition (:183-185).
- Needs decision: no
