### SEP3-1: Relay Bitswap leaks private CIDs to Relays that do not carry the token
- Verdict: PARTIAL. The want-broadcast leak is real: spec/10-relays.md:652 lets Relays use Bitswap "over the libp2p connections they hold for the channel topic", but a libp2p connection is per peer, shared with `v1/agora/discovery` and other topics, and stock Bitswap sends want-haves to every connected peer, so a peer that carries no registration for the token learns the CID and the requester's interest in it. That is outside §5 item 4 ("CIDs it replicates to or pulls from other IOs carrying the same routing token"). The serving-side half of the argument is wrong: "the receiver ... serves any CID it holds to any connected peer" discloses nothing new, because `GET /v1/agora/blob/{cid}` is already unauthenticated and token-free (§10.4.4 para 2). A further point the review missed: "under the same rules" cannot cover eager replication, since Bitswap is pull-only.
- Severity: P2 (keep). Private-CID disclosure to parties outside the token's mesh.
- Fix: spec/10-relays.md §10.4.4, delete the bullet "Relays carrying the same token MAY exchange its blobs with Bitswap ... public IPFS DHT." In the **Public IPFS** paragraph change "Bitswap MAY be used for private ciphertext only between known peers: Relays carrying the same token under the CO's agreements (above), the CO archive, and a user's own devices, which find each other through the self-group (§2.6)." to "Bitswap MAY be used for private ciphertext only between a user's own devices, which find each other through the self-group (§2.6), and between those devices and the CO archive. Relays exchange blobs only over the Peer API." guides/relay-operator.md:146 then needs only "and permits Bitswap for private ciphertext only between relays carrying the same token" changed to "and permits Bitswap for private ciphertext only among a user's devices and the CO archive".
- Needs decision: yes, small. agora-ipfs records "Bitswap among known peers only" without listing which peers; the fix narrows that. (a) delete Relay-to-Relay Bitswap (recommended: one transport for replication, the Peer API, which already carries the token); (b) keep it with the constraint "a Relay MUST send wants for a token's blobs only to peers it knows carry that token (members of that token's topic mesh) and MUST NOT use a Bitswap implementation that sends wants to other connected peers", which most off-the-shelf Bitswap stacks do not meet. Plain language: when one relay asks for a file by Bitswap, standard software shouts the request to every relay it is connected to, including ones with no business knowing that file exists. Dropping Bitswap between relays costs nothing because relays already have a request path that only goes to the right peers.

### SEP3-2: A Relay may publish public content to public IPFS but cannot identify it
- Verdict: REJECTED. (1) The identification claim is wrong on both counts. For public broadcast channels the Relay has a signal: "the CO publishes the channel's `BroadcastKey` and the subscriber form of its `ChannelAdmissionKey` as public Space state ... anyone, including an IO, can map that channel's token" (spec/03-spaces.md:313), and ARCHITECTURE §5 item 6 puts that mapping inside the budget ("except the token of a `keyAccess: public` broadcast channel"), listed as an accepted cost in §9 ("Public broadcast channels are mapped to their Space"). Using an in-budget mapping does not violate S1. For CO-published records the claim "there is no signal at all" is also wrong: §10.4.3 has the Relay store "records a CO explicitly publishes (such as SpaceAds, directory documents and public Space state)", which reach it as signed public records on `v1/agora/discovery`, not under a token. A Relay that guesses instead of checking is already in breach of the existing MUST NOT. (2) The retention/S2 argument is an accepted cost: ARCHITECTURE §9 "Public content on the public IPFS network cannot be withdrawn ... MAY be published to the public IPFS network (protocol spec §10.4.4)", and agora-ipfs: "public content may go on public IPFS". Content the CO made public can be copied by any reader, so a Relay copying it makes no decision the CO has not already made. The guide's choice not to publish is a MAY not exercised, not a contradiction.
- Severity: none.
- Fix: none required. Optional accuracy fix, guides/relay-operator.md:146: replace "because it cannot tell public content from ciphertext by looking at the bytes" with "because doing so safely means tracking which tokens public Spaces publish, which this relay does not do".
- Needs decision: no.

### SEP3-3: Pull-through and `seed` are keyed to the current token, so blobs from before a rotation cannot move to a new Relay
- Verdict: CONFIRMED, and wider than reported. Peer pull answers "404 if this relay does not hold the CID under that token" (spec/10-relays.md:174-176); clients fetch "with `token` set to the channel's current `channelToken`" (:654); new Relays get only "every current key" (:871, :550), and old keys are deregistered shortly after rotation (:582). So pull-through and `seed` cannot recover any blob uploaded before the last rotation. The review missed that the same rule breaks pinning at Relays that already hold the blob: spec/11-transport.md:197 pins only "each listed CID that it holds under that token", and §10.4.4 "Pinning" pulls a CID "it does not hold under that token", so a pin under the current token for a pre-rotation blob held under the old token pulls from peers, gets 404, and answers `unknown-cid`; the blob then expires at its old retention. It also blocks pull-through between existing Relays when `replicationFloor` is less than the number of Relays. Separation check: the review is right that removing the token check from the peer GET costs nothing, because the client GET already serves every held blob to anyone without a token.
- Severity: P2 (keep). Silent loss of pinned and replicated blobs after every removal; CO archive is optional.
- Fix (recommended option a, a deletion rather than chain tracking): spec/10-relays.md §10.2.2, peer GET: change "Pull of one blob held under channelToken (§10.4.4). Response: 200 with the blob bytes, or 404 if this relay does not hold the CID under that token." to "Pull of one blob (§10.4.4). The requester sets `token` to the token under which it will store the blob; the responder does not check it. Response: 200 with the blob bytes, or 404 if this relay does not hold the CID." §10.4.4 para 1: change "Each blob is held under the `channelToken` for which it was uploaded or replicated." to "Each blob is held under every `channelToken` for which it was uploaded, replicated, pulled or pinned, and is charged to and retained for each such token's agreement." §10.4.4 **Pinning**: change "for a CID it does not hold under that token" to "for a CID it does not hold". spec/11-transport.md:197: change "each listed CID that it holds under that token" to "each listed CID that it holds, adding the pin's token as a holder of it,". §10.4.5: change "looks up the `channelToken` under which the CID was stored or pinned and the agreement under which that token is registered, and SHOULD forward the request ... to the CO at the agreement's `contact`" to refer to "each `channelToken` ... and each agreement". DM handover (spec/04-access-control.md §4.6.4): add "Blobs uploaded before a handover stay at the old host's Relays until it deregisters (30 days, below) and in members' stores; a client that needs such an attachment after that re-uploads it under the new token."
- Needs decision: yes. (a) token-free peer GET and pins that attach to any held copy, as above (recommended: removes a check that protects nothing, no new state); (b) the review's chain-aware rule: a Relay answers for a CID held under any token in the requested token's `replaces` chain under the same agreement, which makes Relays track `replaces` (today "Other IOs ignore `replaces`", :854) and still fails across agreements and DM handover; (c) accept the loss and say in §10.4.4 that a Relay added after a rotation, and pins after a rotation, cover only blobs uploaded under the current key unless the CO keeps an `archive`. Plain language: every time someone is removed from a channel, the channel's relay password changes, and relays currently refuse to hand each other files filed under the old password, so older attachments can't be kept or copied to a new relay. Since anyone can already download those encrypted files by their ID, the password check between relays protects nothing and can simply be dropped.

### SEP3-4: The lowest-leaf rule for DM handover is not enforced
- Verdict: CONFIRMED. spec/04-access-control.md:266 assigns the handover to the lowest-index non-logger member, but the only receiver check (:271) is "while the host's user is still a member"; with consentless removal (:201, agora-dm-removal) any member can remove the host's user and race its own handover Commit, which the canonical-Commit rule may accept. The review's fix has a defect it does not mention: the 24-hour window is not checkable by receivers. DM groups have no sequencer stamp, and routing envelope `ts` is sender-chosen and admitted when "older than the `retentionDays`" bound is not exceeded (spec/11-transport.md:184), so a member can backdate the removal Commit's envelope by more than 24 hours and then commit a handover that appears to fall after the window. Even with the rule, a member can remove every lower leaf first; that is visible in the group and consistent with agora-dm-removal ("Controlled membership = use a private Space channel").
- Severity: P3 (keep). Bounded by §9's host-plus-relay bullet; impact is traffic linkage for one DM, not content.
- Fix (constraint: drop the timer, reuse consentless removal): spec/04-access-control.md §4.6.4 para 2, replace "The client of the remaining member with the lowest leaf index, other than a compliance logger or recorder, does this automatically; if no handover Commit has arrived 24 hours after the host's user ceased to be a member, any remaining member's client does it." with "The client of the remaining member with the lowest leaf index, other than a compliance logger or recorder, does this automatically. If that member does not, any member MAY remove it (§4.6), which makes the next member the successor." In para 3, after the existing policy-violation sentence add: "Members MUST also treat as a policy violation a Commit that changes `agora_admission_host` and was not committed by the remaining member with the lowest leaf index, other than a compliance logger or recorder, in the epoch the Commit applies to."
- Needs decision: yes. (a) lowest-leaf only, no 24-hour fallback, stalled successor removed by any member (recommended: fully checkable from the ratchet tree, no clocks); (b) the review's version, lowest leaf within 24 hours then anyone, measured by each receiver's own processing time (members who were offline will disagree, and a Commit accepted by some and rejected by others forks the group); (c) leave it unenforced and extend the §9 host-plus-relay bullet to say any DM member can re-home the group. Plain language: when the person whose server runs a group chat leaves, the job is supposed to pass to a predictable next person, but nothing stops anyone else from grabbing it. The fix makes everyone's app reject a grab by the wrong person, and if the right person is asleep at the wheel, the others can drop them so the job moves on.

### SEP3-5: `chunkCount` "MUST NOT be sent to any IO" contradicts the root block every IO receives
- Verdict: CONFIRMED. spec/05-messaging.md:328 "`contentKey`, `chunkCount` and `sha256` travel only inside the encrypted Message and MUST NOT be sent to any IO" versus spec/14-jmap.md:133, where the uploaded root block has one link per chunk and "reveals only the chunk count and the ciphertext length". No separation loss (within §5 item 4).
- Severity: P3 (keep).
- Fix: spec/05-messaging.md:328, replace "`contentKey`, `chunkCount` and `sha256` travel only inside the encrypted Message and MUST NOT be sent to any IO." with "`contentKey` and `sha256` travel only inside the encrypted Message and MUST NOT be sent to any IO. The `chunkCount` property also travels only inside the Message, though the root block discloses the same count to IOs (§14.3.4)."
- Needs decision: no.
