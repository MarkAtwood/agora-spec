### CRY4-1: The no-sequencer 5 s rule is undefined for Commits a member receives from history, and a member on a losing branch has no failure path
- Severity: P2
- Location: spec/05-messaging.md:34
- Evidence: "a member that receives a Commit for epoch N keeps its epoch N state and collects every Commit for epoch N that arrives within 5 seconds of the first. It then applies the Commit whose envelope `id` (§5.2.2) is lowest, compared as bytes, and discards Commits for epoch N that arrive later." and "A Commit delayed by more than the window at some members but not others splits the group; members left on the losing branch cannot process later traffic and must be removed and re-added."
- Problem: The rule is defined only by arrival time. A member that was offline (normal for DM members on phones) fetches the competing Commits for epoch N from relay history in one batch, so for it every Commit "arrives" at once and it picks the lowest `id`. Online members picked the lowest `id` among Commits that arrived within 5 s of the first and discarded a later, stale Commit even if its `id` is lower. Whenever history holds a stale Commit for an epoch (a member that committed before receiving a Commit more than 5 s old), each catch-up member applies it with probability about one half and forks. Nothing tells the forked member it is on the losing branch or what to do; "must be removed and re-added" names no actor and no trigger. This applies to every DM group, every self-group and every Space without a sequencer.
- Fix: In §5.1.1 "No sequencer", add: "A member that obtains Commits for epoch N from history (§5.2.5), or that holds epoch N state when a Commit for epoch N+1 or a later envelope arrives, applies the Commit for epoch N under whose resulting epoch the later envelopes open (§5.2.2); only if no later envelope exists does it apply the lowest `id`. A member that, after applying a Commit for epoch N, holds envelopes for 60 seconds that open under no sealing key it holds and that no Commit it can obtain explains, deletes its state for the group and tells its user that a member must re-add it, as for Commits past relay retention (§5.2.5)." The sealing key is derived from the epoch secret, so an envelope that opens identifies the branch the group continued on.
- Needs decision: yes. (a) Later traffic decides the branch for catch-up members, plus the delete-and-re-add failure path (recommended). (b) Keep the arrival rule and add only the failure path, and list catch-up forks as an accepted limit in §12. (c) Require a sequencer for DM groups (contradicts "DM groups have no Space and no sequencer", §14.4.1; not recommended). Plain language: a phone that was offline sees two competing changes at once and can pick the other one from the members who were online, after which it can read nothing. Option (a) lets it pick the change that later messages were built on, and tells it to ask to be re-added if it still cannot read.

### CRY4-2: `closingHeads` races a still-running old sequencer and members holding stale Space state, with no recovery for a member that applied a rejected Commit
- Severity: P2
- Location: spec/14-jmap.md:257; spec/05-messaging.md:29, :31
- Evidence: §14.4.5: "the Space state change that names a new `sequencer` DID carries `closingHeads` ... which the CO chooses from the old sequencer's log or from relay history ... On that stream members accept a stamp signed by the old DID only at or below the head ... every later position, and every stamp on another branch, is rejected". §5.1.1: "A member MUST NOT apply such a channel's Commit unless its stamp ... verifies per §13.1.1 as signed by the `sequencer` DID in the Space state the member holds". §14.4.5 Equivocation: "A client that detects one MUST stop applying that stream after the fork point".
- Problem: Three gaps. (1) Nothing makes the old sequencer stop stamping before the CO reads its head. The CO picks the head at time T; the old sequencer keeps stamping the current token's commit stream until the rotation registration reaches it (or forever, if the CO has ended that agreement and sends it nothing). Members that have not yet fetched the new Space state still accept those stamps and apply Commits above the head; members with the new state reject them. MLS state cannot be rolled back, so the group forks. (2) A member that already applied a Commit above the head, or on the branch the CO did not choose, has no rule: it is ahead on a dead branch and every later Commit fails to open. The only failure path in §5.1.1 covers a gap it cannot fill, not a Commit it already applied. (3) A member holding the old state ignores stamps by the new DID, and after a removal of `sequencer` it rejects every unstamped Commit, with no rule telling it to refetch Space state first; it stalls until some unrelated trigger (a `SpaceStateHead` notice, reconnect) makes it refetch.
- Fix: §14.4.5 Replacement, before "Commit streams close by the same rule": "Before it chooses the heads, the CO deregisters the channels' admission keys at the old sequencer (§10.5.3), or ends its agreement, so that it stamps nothing more, and then reads each commit stream to its end." §5.1.1, after the stamp verification sentence: "A member that receives a Commit whose stamp is signed by a DID other than the `sequencer` it holds, or an unstamped Commit in a channel whose Space state it holds names a sequencer, fetches the current Space state head (§3.4) before it rejects the Commit." And after the gap failure path: "A member that finds it has applied a Commit that a later Space state's `closingHeads`, or the fork rule of §14.4.5, rejects deletes its state for the group and tells its user that a member must re-add it."
- Needs decision: no

### CRY4-3: Any DID the admission host serves can forge a committed confirmation and make the host deregister the group's live key 7 days later
- Severity: P2
- Location: spec/04-access-control.md:175; spec/12-security.md:69, :71
- Evidence: §4.6: "For each POST that issues a key, the host generates a new key whose `keyEpoch` is one more than the last it issued for that `<groupID>` ... records the requesting DID as the key's **issuee**" and "the host accepts them only from a DID it serves" and "Seven days after it receives the confirmation of a key, the host deregisters every earlier key of that group on its own". §12.5: "A key that was issued but never committed is never confirmed, so it does not cause the current key's deregistration." and "The DID a DM admission key was issued to can deregister it at once".
- Problem: The host keeps no member list (binding), so it cannot tell whether the confirming DID's key was ever committed. A former member that shares the admission host (for example a coworker removed from a DM, or any DID the host serves that learned the group ID, such as from a compliance archive, §12.11) POSTs for the group, receives key k, and POSTs `/k/committed`. Seven days later the host deregisters every earlier key, including the key in the current GroupContext and every previous one. Members then have no admitted key under which to publish the rotation or move Commit (§4.6), so the group is stranded. §12.5 states the opposite, and the accepted limit there covers only a DID deleting a key that was issued to it, which a rotation after its removal would have ended.
- Fix: one of the options below, then make §12.5:69 and :71 match.
- Needs decision: yes. (a) Accept it: rewrite §12.5 "Removed host's user withdraws the DM key" to "Any DID that the admission host serves and that knows the group ID, including every former member served by that host, can strand the group: it can deregister a key issued to it at once, or have a key issued and confirm it, after which the host deregisters every earlier key 7 days later. Members start a new group." and delete the "never confirmed" sentence (recommended; same attacker class and outcome as the accepted `agora-dm-withdraw-limit`, no new mechanism). (b) Proof of possession: the confirmation body carries an Ed25519 signature, with the seed of the key the Commit replaced, over `agora/v1/dm-confirm || groupID || keyEpoch`; the host deregisters earlier keys only if it verifies under a key it issued for that group, since only current members read the replaced key from the GroupContext (adds a label to §13.3 and does not cover a move-in, where the replaced key belongs to another host). (c) Drop the 7-day cap (reverses `agora-dm-key-cap`; not recommended). Plain language: today a person who was removed from a direct-message group, and who uses the same key server as someone still in it, can tell that server a fake "new key is in use" and a week later the group's real key stops working. Option (a) writes that down as a known limit; option (b) makes the server ask for proof that the sender holds the group's current key.

### CRY4-4: §10.5.3's generic registration-service rules apply to DM admission hosts and contradict §4.6
- Severity: P2
- Location: spec/10-relays.md:820, :878, :882; spec/04-access-control.md:175
- Evidence: §10.5.3: "for a DM group or a self-group (§2.6), by the group's admission host"; "**When the CO deregisters.** After a rotation, the registration service deregisters the previous key once members have had time to move to the new token, after a grace period RECOMMENDED to be 300 seconds."; "It MUST also re-send every current key to each IO at least once every 24 hours." §4.6: "Until a later key is confirmed, the host keeps an earlier key registered until its issuee DELETEs it or the host deregisters it under §2.5.6." and "For each group the host keeps only the last `keyEpoch` it issued and, for each key it has not deregistered, that key's issuee and when its confirmation arrived, if it has."
- Problem: A host that follows §10.5.3 deregisters the previous key 300 s after it issues a new one. In a DM the host sees only issuance, so this fires on a POST whose key never wins (a losing competing rotation, §4.6 Rotation) and kills the key the group is using; it is exactly the stranding that the DELETE-after-admission rule and the 7-day cap exist to prevent. Separately, "keeps only" leaves the host without the `channelToken` and public key of each live key, which it needs for the 24-hour re-send, for re-registration after a Relay loses state (§10.4.7) and for any `AdmissionKeyDeregistration` (which lists `channelTokens`). Also, a host cannot know which key is "current", only which are not deregistered.
- Fix: §10.5.3 "When the CO deregisters", add: "A DM group's or self-group's admission host does not deregister on rotation; it deregisters only as §4.6 states." §10.5.3 re-send sentence: "every current key (for an admission host, every key of a DM group or self-group it has not deregistered)". §4.6:175: replace "keeps only the last `keyEpoch` it issued and, for each key it has not deregistered, that key's issuee and when its confirmation arrived, if it has" with "keeps only the last `keyEpoch` it issued and, for each key it has not deregistered, that key's `channelToken`, public key, issuee and when its confirmation arrived, if it has".
- Needs decision: no

### CRY4-5: The Space's own MLS group has no admission key, token, commit stream or closing head
- Severity: P2
- Location: spec/03-spaces.md:175; spec/05-messaging.md:289, :27; spec/03-spaces.md:195; spec/04-access-control.md:295
- Evidence: §3.3: "the Space-level `mlsGroupID` is the group ID of the Space's own MLS group". §5.2.2: "For each channel, the CO's registration service generates a random Ed25519 key pair, the **channel admission key**". §3.4: "GET <spaceEndpoint>/admission-key/<channelID>". §5.1.1: "If the group is a channel of a Space whose state designates a `sequencer`". §3.3: "`closingHeads` ... one entry `{channelID, stream, n, hash}` per channel that has an MLS group". §4.8: "A Commit in the Space's own group whose self-Removes cover every leaf of a member DID is that member's notice of leaving."
- Problem: The Space's own group is not a channel and has no `channelID`, so no rule issues, registers or serves its admission key, no `channelToken` exists for it, and relays cannot admit any of its envelopes. Its Commits fall under no stated ordering rule in a Space with a sequencer (it is not "a channel"), and `closingHeads` cannot name it. Yet `SpaceStateHead` notices (§3.4) and the leave notice of §4.8, on which the CO's removal of a leaving member depends, travel in it. Implementers will invent different identifiers for its key endpoint and different commit rules.
- Fix: §3.3: "The Space's own group is admitted and ordered as a channel whose `channelID` is the Space-level `spaceChannelID`, 16 random bytes set in the genesis state and never changed; every rule of §3.4, §5.1.1, §5.2.2 and §14.4.5 that names a channel or `channelID` applies to it." Add `spaceChannelID` to the field index and to the genesis requirements in §3.6, and to the access rule of §3.4 ("to every member of the Space").
- Needs decision: no

### CRY4-6: Guest members of a shared channel cannot apply the home Space's canonical-Commit rule
- Severity: P2
- Location: spec/08-cross-space.md:95; spec/04-access-control.md:94; spec/05-messaging.md:27-29
- Evidence: §8.6: "It also serves eligible guest members the home Space's non-member view (§4.4), which carries the shared channel's entry and the admins without `members`: that view MUST include the shared channel's entry and every admin entry whose scope covers it". §5.1.1: "If the group is a channel of a Space whose state designates a `sequencer` ... signed by the `sequencer` DID in the Space state the member holds".
- Problem: A guest holds its own Space's state and the home Space's non-member view. Nothing requires that view to carry the home Space's `sequencer` or `closingHeads`, and §5.1.1 does not say which Space's state decides for a shared channel. A guest whose view lacks `sequencer`, or that reads its own Space's `sequencer`, applies the no-sequencer rule or verifies stamps against the wrong DID, while home members require home-sequencer stamps; the two sets apply different Commits and the group forks, and a guest that publishes an unstamped Commit has it dropped by every home member.
- Fix: §8.6 view sentence: "that view MUST include the shared channel's entry, every admin entry whose scope covers it, and the home Space's `sequencer` and any `closingHeads`". §5.1.1 first bullet: "For a shared channel (§8), the home Space's state decides, as served in that view."
- Needs decision: no

### CRY4-7: The compliance audit chain has no links, and `removalAttempts` mutates a signed entry
- Severity: P2
- Location: spec/07-compliance.md:317-334, :341-354, :403-413; spec/06-calls.md:444-461
- Evidence: §7.8.8: "The regulated member's Space MUST record each DM group compliance logger admission in its IPLD compliance audit chain." The `DMComplianceAuditEntry`, `ComplianceGapEntry`, `ArchiveResealEntry` and `VTCComplianceAuditEntry` bodies carry no previous-entry field, unlike `ComplianceRecord` ("`prevRecordCID` chains records into a linked list, making the log append-only and tamper-evident"). §7.6: "a unified, tamper-evident audit chain". §7.8.8: "`removalAttempts` is an array of timestamps and initiator DIDs for any Remove commits targeting the logger that the regulated member's client detected", in an entry "signed per §13.1.1 by `loggerDID`" at admission.
- Problem: Without a link, deleting a gap entry or an admission entry from the "chain" is undetectable, which defeats the purpose of recording gaps for a regulator; implementers will each invent a linkage or none. `removalAttempts` is filled after the entry is signed, by a party (the regulated client) that is not the signer, so either the logger re-signs a new entry with a new CID that nothing links to the old one, or the field stays empty. The logger already processes the Commit that removes it and records the gap, so the field duplicates `ComplianceGapEntry`.
- Fix: Add `"prevEntryCID": "bafkrei..."` to each of the four audit entry types, defined once in §7.8.8: "Every entry of the compliance audit chain carries `prevEntryCID`, the CID of the previous entry the same signer wrote to the Space's audit chain (`null` for its first), so removing or inserting an entry breaks the chain, as for `prevRecordCID` (§7.4)." Delete `removalAttempts` and its paragraph; add to `ComplianceGapEntry` an optional `removedBy`, the MLS sender of the Remove Commit, which the logger learns when it processes that Commit.
- Needs decision: no

### CRY4-8: A Remove of a listed compliance DID that keeps its `agora_compliance` entry has no defined handling

- Location: spec/07-compliance.md:240, :301
- Evidence: "The Commit that removes every leaf of a listed DID also removes that DID's entry ... Members MUST treat as a policy violation (§4.5) a Commit that adds an entry without adding a leaf of that DID, or that removes or changes an entry otherwise than this paragraph allows." §7.8.5 covers "both are absent" and "the leaf exists without an entry", not an entry without a leaf.

### CRY4-10: "Host's user" is self-asserted, so §12.5's bound on bogus same-host keys does not hold and the handover trigger can be suppressed
- Severity: P3
- Location: spec/04-access-control.md:167, :243; spec/12-security.md:69
- Evidence: "The **host's user** is a member whose identity host, the origin of its `KeyPackageEndpoint` (§5.2.1.1), equals `host`". §12.5: "A bogus same-host key can come only from a host's user, because members reject a same-host change from any other member".
- Problem: A member writes its own `KeyPackageEndpoint`: a `did:key` user in its Pkarr record, an individual `did:webvh` user in its DID document. Any such member can name the current host's origin and become a host's user without being served there. It can then commit same-host bogus keys without a policy violation, and while it stays a member "no host's user remains" never fires, so after the real host's user leaves no member is due to rotate or move and removed members keep admission indefinitely. Content stays safe and the power is within "any member may remove every other member", so P3, but §12.5 overstates.
- Fix: §12.5:69: replace "A bogus same-host key can come only from a host's user" with "A bogus same-host key can come only from a member whose `KeyPackageEndpoint` names that host's origin, which any member that controls its own DID document or Pkarr record can arrange". §4.6.4: "A member that finds the current key not rotated 24 hours after a Commit that removed a leaf moves the group, whether or not a host's user remains."
- Needs decision: no

### CRY4-11: Two DM triggers depend on facts other clients cannot see or that relays report transiently
- Severity: P3
- Location: spec/04-access-control.md:196, :200; spec/10-relays.md:688
- Evidence: §4.6 Rotation: "the client of the host's user with the lowest leaf index among those not holding the group in the message request state (§4.6.3) MUST POST". §4.6: "A member that finds the key in the current GroupContext not admitted by the group's relays, because no Relay in its `relays` that it can reach accepts a Subscribe to its channel token, each answering `unknown-token` (§11.4), rotates the key if it is a host's user and otherwise moves the group". §10.4.7: a Relay that lost registrations "starts with no registrations and answers `unknown-token` for every token".
- Problem: (1) The request state is local, so a host's user cannot know whether a lower-indexed one is in it; the 24-hour fallback catches it, so only delay results. (2) A DM whose relay list has one Relay that restored from backup makes every member see `unknown-token` for the current and earlier keys at once; every non-host member then moves the group, producing competing moves and handing the group to an arbitrary member's host, for a condition that the host's 24-hour re-send repairs.
- Fix: (1) "the client of the host's user with the lowest leaf index MUST POST ...; a client holding the group in the message request state skips this, and the 24-hour rule applies". (2) Add "and only if a Relay in `relays` admits an earlier key of the group, or the condition has lasted 24 hours".
- Needs decision: no

### CRY4-12: Removing `agora_admission` or weakening `required_capabilities` in a DM is not a policy violation
- Severity: P3
- Location: spec/04-access-control.md:179, :196; spec/07-compliance.md:220
- Evidence: "Every DM group and self-group lists it in `required_capabilities`"; "Members MUST treat as a policy violation (§4.5) a Commit that changes `agora_admission`, keeps `host`, and either keeps `key_epoch` or has a committer that is not a host's user."
- Problem: A GCE that omits `agora_admission`, or drops 0xF0A0/0xF0A4 from `required_capabilities`, matches no violation rule (no `host` is kept). The group then has no key to publish under, and the "not admitted" recovery assumes a key exists. Within a malicious member's existing power, but implementers will differ on whether such a group is usable.
- Fix: §4.6: "Members MUST treat as a policy violation a Commit after which a DM group's or self-group's GroupContext lacks `agora_admission` or its `required_capabilities` lacks 0xF0A0 (and, for a DM group, 0xF0A4; for a self-group, 0xF0A3)."
- Needs decision: no

### CRY4-13: Two places still call the no-sequencer rule "lowest-hash", without the window
- Severity: P3
- Location: spec/04-access-control.md:26; spec/03-spaces.md:193
- Evidence: §4.1: "or, with no sequencer, the lowest-hash rule"; §3.3: "competing Commits are resolved by the lowest-hash rule (§5.1.1)". §5.1.1 defines a 5-second collection window and the lowest envelope `id`.
- Problem: An implementer reading §4.1 or §3.3 alone implements lowest-hash over all Commits ever seen, which differs from §5.1.1 for late Commits.

- Needs decision: no
