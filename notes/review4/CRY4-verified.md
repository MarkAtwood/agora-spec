# Review 4: CRY4 verified

Checked against commit 4b76c3d text, `bd memories agora`, ARCHITECTURE §8/§9 and spec §12.5 accepted limits. Overlaps: CRY4-4 merges with IMP4-3 (IMP4-verified.md); CRY4-7 merges with PRI4-5 and IMP4-8 (PRI4-verified.md, IMP4-verified.md).

### CRY4-1: No-sequencer rule undefined for Commits fetched from history; no failure path for a losing branch
- Verdict: CONFIRMED. 05:34 defines the winner only by arrival ("collects every Commit for epoch N that arrives within 5 seconds of the first ... discards Commits for epoch N that arrive later") and names no actor or trigger for "must be removed and re-added". The existing re-add failure paths cover only a sequencer-stream gap (05:31) and Commits past relay retention (05:452). A member catching up from history (05:452 "relay history serves catch-up after a client has been offline") receives all Commits for N together and cannot reproduce the online members' choice. No accepted limit in §12 or ARCHITECTURE §9 covers no-sequencer forks. No binding decision applies: `agora-commit-winner` governs only the sequencer case.
- Severity: P2, keep. Affects every DM group and self-group, the common offline-phone case.
- Fix (option a): spec/05-messaging.md:34, after "The committer applies the same rule to its own Commit, counting from when it published it.", insert: "A member that holds more than one Commit for epoch N when it first processes epoch N, as after fetching history (§5.2.5), and also holds an envelope that opens under the sealing key (§5.2.2) of the epoch one of those Commits creates and of no other, applies that Commit; otherwise it applies the Commit with the lowest `id`." Replace "members left on the losing branch cannot process later traffic and must be removed and re-added." with "a member that applied a Commit for epoch N and then drops an envelope that opens under no sealing key it holds (§5.2.2) after processing its next Commit, and that obtains no Commit that explains it, deletes its state for the group and tells its user that a member must re-add them, as for Commits past relay retention (§5.2.5)." Reuses the existing buffer-then-drop rule of 05:311 instead of a new 60-second timer.
- Needs decision: yes. Options: (a) later traffic picks the branch for catch-up members, plus the delete-and-re-add failure path (recommended); (b) keep the arrival rule, add only the failure path, and add "No-sequencer forks" as an accepted limit in §12.5; (c) require a sequencer for DM groups (contradicts 14:159 "DM groups have no Space and no sequencer"; not recommended). Plain language: a phone that was offline sees two competing changes at once and may pick a different one from the members who were online, after which it can read nothing. Option (a) lets it pick the change that later messages were built on, and tells the user to ask to be re-added if it still cannot read.

### CRY4-2: `closingHeads` races a still-running old sequencer and stale Space state
- Verdict: CONFIRMED, all three parts. (1) 14:257 orders the steps "a Space state change, then rotates the admission keys"; the old sequencer stops stamping a commit stream only on a registration with `replaces` (10:858, 14:170), so it can stamp above the head the CO already chose, and members still holding the prior Space state accept those stamps (05:29 "signed by the `sequencer` DID in the Space state the member holds"). (2) No rule covers a member that already applied a Commit above the head or on the unchosen branch; 14:256 says only "stop applying that stream after the fork point", and 04:143 covers policy violations, not this. (3) The only refetch-before-reject rule is for authorization (05:33, `agora-commit-authz`); a stamp by an unknown DID or an unstamped Commit is simply rejected, and 03:323 refetch triggers are SHOULDs on notice or reconnect.
- Severity: P2, keep.
- Fix: as proposed in CRY4.md, unchanged:
  - spec/14-jmap.md:257, before "Commit streams close by the same rule": "Before it chooses the heads, the CO deregisters the channels' admission keys at the old sequencer (§10.5.3), or ends its agreement, so that it stamps nothing more, and then reads each commit stream to its end."
  - spec/05-messaging.md:29, after the stamp verification sentence: "A member that receives a Commit whose stamp is signed by a DID other than the `sequencer` it holds, or an unstamped Commit in a channel whose Space state it holds names a sequencer, fetches the current Space state head (§3.4) before it rejects the Commit."
  - spec/05-messaging.md:31, after the gap failure path: "A member that finds it has applied a Commit that a later Space state's `closingHeads`, or the fork rule of §14.4.5, rejects deletes its state for the group and tells its user that a member must re-add them."
  A deregistration does not bind a malicious old sequencer; the third sentence is the failure path for that case.
- Needs decision: no

### CRY4-3: Any DID the admission host serves can confirm a key it never committed and strand the group 7 days later
- Verdict: CONFIRMED. 04:175: the host issues to any "DID it serves", records it as issuee, accepts the confirmation "only from the key's issuee", and "Seven days after it receives the confirmation of a key, the host deregisters every earlier key of that group on its own". Nothing ties the confirmation to a winning Commit; the host keeps no member list (`agora-dm-key-in-group`). 12:69 "A key that was issued but never committed is never confirmed, so it does not cause the current key's deregistration" is false against a dishonest issuee. The accepted limit at 12:71 (`agora-dm-withdraw-limit`) covers only a removed host's user deleting its own key. After the cap fires, members hold no admitted key, so the move recovery at 04:196 also fails.
- Severity: P2, keep.
- Fix: depends on the decision. For (a): spec/12-security.md:71, replace the bullet with: "**A DID served by the admission host strands the DM.** Any DID that the group's admission host serves and that knows the group ID, including every former member served by that host, can strand the group: it can deregister a key issued to it at once, or have a key issued for the group and confirm it, after which the host deregisters every earlier key 7 days later (§4.6). Relays then refuse every envelope under the group's keys, including a Commit that would move the group (§4.6.4), and its members start a new group. This is an accepted limit." Delete from 12:69 the sentence "A key that was issued but never committed is never confirmed, so it does not cause the current key's deregistration." Change the recovery sentence at 04:196 ("and the host deregisters it on its own only 7 days after the issuee of a later key confirms that key's Commit (above)") to end "... confirms a later key (above)".
- Needs decision: yes. Options: (a) accept and document (recommended: same attacker class and outcome as the accepted `agora-dm-withdraw-limit`, no new mechanism); (b) proof of possession: the confirmation carries a signature under the seed of the key the Commit replaced, which only current members read from the GroupContext (adds a label to §13.3, and does not cover a move-in, where the replaced key belongs to another host); (c) drop the 7-day cap (reverses `agora-dm-key-cap`; not recommended). Plain language: someone removed from a direct-message group who uses the same key server as a remaining member can tell that server a fake "new key is in use", and a week later the group stops working. Option (a) writes this down as a known limit; option (b) makes the server ask for proof that the sender held the group's previous key.

### CRY4-10: "Host's user" is self-asserted, so §12.5's bound on bogus same-host keys does not hold
- Verdict: PARTIAL. CONFIRMED that the status rests on the member's own `KeyPackageEndpoint` origin (04:167), which an individual sets in its own DID document or Pkarr record, so 12:69 "A bogus same-host key can come only from a host's user" overstates. Overstated: removed members do not "keep admission indefinitely". The departing real host's user's client DELETEs its current key 30 days after its removal (04:247), so the actual outcome is that the group strands after 30 days if nobody moves it. That is within the existing "remove every other member" power (12:69) and the accepted `agora-dm-withdraw-limit` outcome.
- Severity: P3, keep.
- Fix: spec/12-security.md:69: replace "A bogus same-host key can come only from a host's user, because members reject a same-host change from any other member (§4.6)." with "A bogus same-host key can come only from a member whose `KeyPackageEndpoint` names that host's origin (§4.6), which any member that controls its own DID document or Pkarr record can arrange." For option (b) only, add to spec/04-access-control.md:243 (§4.6.4): "If no Commit that changes `agora_admission` has arrived 24 hours after a Commit that removed a leaf, any remaining member's client other than a DID listed in `agora_compliance` moves the group, whether or not a host's user remains."
- Needs decision: yes. Options: (a) correct the §12.5 sentence only and treat the fake host's user as within existing member power (recommended; no behavior change); (b) also add the 24-hour move fallback above. Option (b) also moves the group away from a real host's user who is offline for more than 24 hours after a removal, which reverses the accepted "rotation waits until a host's user's client is online" (04:200, 12:68). Plain language: a member can pretend to belong to the group's key server, which the security section says is impossible. Option (a) fixes that sentence; option (b) also lets any member take over the group if nobody rotates its key within a day, at the cost of moving groups away from people who are briefly offline.
