# 4. Access Control and Moderation

> Binds: both. Source: import/agora-protocol-spec-unified.md lines 2357–2509 (§9).


*Binds: both.*

## 4.1 Keyholders

Agora uses a three-tier authority model. Each tier's permissions are enforced cryptographically: an operation not signed by a key with the required authority MUST be rejected by conformant clients. Relays do not evaluate Space authority; their only access control is the MLS-membership proof (ARCHITECTURE §6.2).

**Space Owner:** holds the signing key for the Space state document. The Space Owner has sole authority to transfer or delete the space, grant or revoke the Admin role, and sign Space state mutations affecting top-level structure. There is exactly one Space Owner at any time. Ownership transfer is executed via a signed `SpaceState` mutation that replaces the `owner` DID, signed by the current owner.

**Channel/Space Admin:** a role granted by the owner and recorded in the Space state document. Admins can sign Space state mutations within their granted scope, issue invites, execute moderation operations within channels they administer, and add or remove members from channel MLS groups within their scope.

**MLS Group Committer:** by default, any current MLS group member may issue Commit messages (RFC 9420 default). Space operators MAY restrict Commit authority to a designated keyholder set via a `commitPolicy` field in the channel state. Restricting commits to a smaller set is recommended for large public channels to prevent epoch racing and Commit conflicts.

## 4.2 Space Roles

Roles beyond Owner and Admin are defined freely in the Space state document and enforced through MLS group membership. A user's assigned role determines which channel MLS groups they are added to when they join. Role assignment is a Space state mutation signed by an Admin or Owner.

```json
"roles": [
  {
    "id": "member",
    "label": "Member",
    "color": "#5865F2",
    "channelAccess": ["general", "engineering/*"],
    "canInvite": false
  },
  {
    "id": "engineer",
    "label": "Engineer",
    "color": "#57F287",
    "channelAccess": ["general", "engineering/*", "voice/*"],
    "canInvite": true
  }
]
```

`channelAccess` is a list of channel path globs. When a user is assigned a role, they are added to the MLS groups for all matching channels via a Commit signed by the Admin performing the assignment.

## 4.3 Invite Flow

Invites are signed tokens linking a specific DID (or an open link) to a Space and an optional role:

```json
{
  "@type": "SpaceInvite",
  "space": "agora://bafyrei...",
  "issuedTo": "did:key:z6MkInvitee...",
  "role": "member",
  "issuedBy": "did:key:z6MkAdmin...",
  "expiresAt": "2026-04-12T00:00:00Z",
  "maxUses": 1,
  "spaceEndpoint": ["https://spaces.example.com/v1/agora/space/1f3a..."]
}
```

The invite is signed per §13.1.1 by `issuedBy`. `spaceEndpoint` lists the CO's Space endpoint URLs, from which the invitee fetches Space state (§3.4).

Link-based invites (no `issuedTo` field) are supported for public spaces. These use a random token that resolves to a signed invite document via an endpoint operated by the issuing CO, not by a Relay (ARCHITECTURE §7 item 4). Every invite code or token MUST carry at least 128 bits generated by a cryptographically secure random number generator. Link-based invites support a `maxUses` limit; setting `maxUses: 0` means unlimited uses until the expiry date.

**Revocation.** An invite MAY be revoked before `expiresAt` by an `InviteRevocation`, signed per §13.1.1 by the invite's `issuedBy`, the Space owner or an admin (§4.1):

```json
{
  "@type": "InviteRevocation",
  "space": "agora://bafyrei...",
  "inviteCID": "bafyrei...",
  "revokedBy": "did:key:z6MkAdmin...",
  "ts": "2026-04-01T00:00:00Z"
}
```

`inviteCID` is the CID of the signed `SpaceInvite`; the revocation does not repeat `issuedTo`. It is distributed like moderation records (§4.5): referenced from the Space state chain and served by the Space endpoint (§3.4). Clients MUST validate an `InviteRevocation` against current Space state and MUST ignore one whose signer is not the invite's issuer, the owner or an admin. The Space endpoint MUST NOT resolve a link token to, serve state against, or count a use of a revoked invite. A client MUST NOT add a member to any of the Space's MLS groups on the strength of a revoked invite. Revocation is permanent; re-inviting requires a new invite.

**Welcome acceptance.** A client MUST accept an MLS Welcome to a Space channel group only if the adding member's credential identifies a DID authorized to add members to that channel under current Space state (§4.1, §4.2). A client MUST reject a Welcome whose adder cannot be authenticated from the group's ratchet tree, and MUST reject a Welcome for a group ID for which it already holds group state; a Welcome never replaces an existing group. A client MUST reject a Welcome whose group ID (RFC 9420 GroupContext `group_id`) differs from the `mlsGroupID` that current Space state declares for that channel, or for the Space's own group (§3.3). If no channel in the client's copy of Space state declares that group ID, the client MUST fetch the current Space state (§3.4) before deciding.

## 4.4 Private Channels

A channel is private if its MLS group membership is a strict subset of the Space's member list. The channel's existence MAY be hidden from non-members: the channel path is omitted from the view of Space state that the CO's Space endpoint (§3.4) serves to non-members, and that access-controlled view is signed by the space owner or a delegated admin. Only the Space endpoint serves Space state to non-members; no Relay does. Non-members have no way to enumerate private channels they are not members of.

## 4.5 Moderation Operations

All moderation records (`BanRecord`, `TimeoutRecord` and the moderation log) are verified outside any MLS group and are signed per §13.1.1 by a CO key (the Space owner or an admin) and distributed like Space state (§3.4): referenced from the Space state chain, served by the Space endpoint, and announced to members in-band. Clients validate each record against current Space state, checking that the signer holds the required role and scope, and MUST ignore records that fail validation. Relays do not enforce moderation records (ARCHITECTURE §6.2).

**Kick:** removes a member from one or more channel MLS groups without a space-level ban. The Admin issues MLS Remove commits for the target DID across the relevant channel groups. The member retains space membership and may be re-added to channels by an Admin.

**Ban:** removes a member from all space channel MLS groups and records a signed `BanRecord` in the space's moderation log:

```json
{
  "@type": "BanRecord",
  "space": "agora://bafyrei...",
  "target": "did:key:z6MkBanned...",
  "reason": "spam",
  "bannedBy": "did:key:z6MkAdmin...",
  "ts": "2026-03-12T12:00:00Z"
}
```

The ban takes effect through the MLS Removes: the banned member does not hold the access key of any later epoch, so Relays reject its envelopes without learning its DID (ARCHITECTURE §6.2). Relays do not keep DID ban lists. Clients MUST reject a Commit that adds a DID with a standing `BanRecord` to any of the Space's channel groups.

> **Open (agora-pozi.8):** the epoch access proof (§5.2.2) awaits external cryptographic review.

**Timeout:** a time-bounded moderation action with an `expiresAt` field. Timeouts are client-enforced: members' clients MUST discard application messages from the target DID in that space until expiry. Relays do not enforce timeouts (ARCHITECTURE §6.2). MLS group membership is not affected; the user remains a group member and can receive messages, and can still send ciphertext that other members' clients discard.

```json
{
  "@type": "TimeoutRecord",
  "space": "agora://bafyrei...",
  "target": "did:key:z6MkMuted...",
  "expiresAt": "2026-03-12T13:00:00Z",
  "issuedBy": "did:key:z6MkAdmin..."
}
```

**Message Delete:** a JMAP Chat `Message` retraction (§5.2.3): an MLS application message whose body carries the target's `senderMsgId`, `deletedAt`, and `deletedForAll: true`. The original author may retract their own message. A keyholder with Admin authority over the channel (§4.1) may retract any member's message in that channel. The retraction carries no object signature; its MLS sender signature identifies the sender (§13.1.1). Clients MUST apply a retraction only if its MLS sender is the sender of the target Message or holds Admin authority over the channel under current Space state, and MUST ignore it otherwise. Relays cannot read retractions, which travel inside ciphertext, and do not enforce them (ARCHITECTURE §7 item 2). The message CID remains in the IPLD history DAG as a tombstone entry.

**Moderation Log:** all moderation actions are appended to a signed IPLD linked list. The tail CID is referenced in the Space state document. The log names members, so it is served to space members only by the Space endpoint and MUST NOT be stored on IO infrastructure except as group-encrypted blobs (§3.4). This log is readable by space members and provides an auditable record of who moderated whom and when, with no ability to retroactively delete entries.

## 4.6 Direct Message Channels

A **Direct Message (DM) channel** is an MLS group established between two or more users outside of any Space's channel hierarchy. DM groups are not owned by any Space and do not appear in any Space state document. They are identified by a `DMGroupCID` (the IPFS CID of the `DMGroupDescriptor` document) and are routed like any channel, on `v1/agora/channel/<dmGroupToken>`, so relays cannot distinguish DM traffic from channel traffic;  `dmGroupToken` is derived each epoch from the MLS exporter as `MLS-Exporter("agora-dm-token", "", 32)` and rotates on every epoch exactly as a channel token does. It MUST NOT be derived from the MLS group ID or any other value that is constant across epochs.

**DMGroupDescriptor schema:**

```json
{
  "@type": "DMGroupDescriptor",
  "schemaVersion": "1",
  "dmGroupID": "urn:agora:dmgroup:<uuid>",
  "mlsGroupID": "base64url...",
  "created": "2026-03-12T00:00:00Z",
  "createdBy": "did:key:z6MkCreator...",
  "members": [
    "did:key:z6MkAlice...",
    "did:key:z6MkBob..."
  ],
  "complianceLoggers": []
}
```

`members` is the initial member DID list. `complianceLoggers` is the list of `ComplianceLogger` DIDs that have been admitted to the group under §7.8. The `DMGroupDescriptor` is updated (new CID) on every membership or logger change. Because it lists member DIDs, it travels only inside the group: the committer of each change sends the updated descriptor to the group as an MLS application message in the new epoch, and members keep it locally. As an inside-group object it carries no object signature; the committer's MLS sender signature authenticates it (§13.1.1). It MUST NOT be stored on IO infrastructure except as a group-encrypted blob (§3.4).

**MLS group initialization:** The DM group creator generates a fresh MLS group, adds KeyPackages for each invited member, and delivers each Welcome by POST to the `KeyPackageEndpoint` in the invitee's DID document (§7.8.2), the endpoint the KeyPackage was fetched from, so delivery reveals nothing to that endpoint beyond what the KeyPackage fetch already did. A Welcome is not sent on any gossipsub topic. There is no Space admin in the invite path; any DM group member may add new members via standard MLS Add + Commit, subject to the consent mechanism in §4.6.1. A client MUST accept a DM Welcome only from an adder authenticated from the group's ratchet tree as a member of the group, MUST NOT accept an anonymous Welcome, and MUST reject a Welcome for a group ID for which it already holds group state. `mlsGroupID` in the `DMGroupDescriptor` is the MLS group ID of the DM group. A client MUST ignore a `DMGroupDescriptor` whose `mlsGroupID` differs from the group ID of the group it was received in, and MUST leave a DM group joined by Welcome if the first descriptor it receives there names a different `mlsGroupID`.

The `KeyPackageEndpoint` is hosted by whoever runs the recipient's identity (§5.2.1.1), so only that host observes Welcome deliveries.

**Relay routing:** Because DM groups have no Space affiliation, Relays route DM traffic by `dmGroupToken` alone, identically to channel traffic. A Relay that does not know the `dmGroupToken` will not route DM traffic; the sending client SHOULD use the Relays known to be serving the recipient's DID (discoverable from the recipient's DID document relay hints).

**Cross-topology reachability.** DM reachability is determined by the recipient's relay hints, not by their DID method or the topology of either party's relay. A user with a `did:web:agency.example` identity can initiate a DM with a user whose only relay hint is a `.onion` address; the initiating client connects to that `.onion` relay via Tor (if available) or routes through an intermediary relay that has Tor reachability. Neither relay learns the other party's identity; relay blindness (§10.4.1) holds across topology boundaries. The only requirement is that the initiating client, or a relay it controls, can reach at least one of the recipient's advertised relay hints. DID method, DNS anchoring, and relay topology are orthogonal to whether two users can exchange messages.

**History and storage:** DM message history is stored in IPFS/IPLD identically to channel history. The `DMGroupDescriptor` CID is the root; history stored on IO infrastructure references the descriptor by CID without containing it in the clear. Members are responsible for pinning their own DM history; there is no Space-level pinning obligation.

### 4.6.1 Member Addition Consent

Any DM group member MAY propose adding a new member via an MLS Add Proposal. The Add is not committed until a configurable consent threshold of existing members issues a matching Commit or explicit approval signal. The default consent model is **unanimous** for groups of 2–4 and **majority** for groups of 5 or more. The `DMGroupDescriptor` MAY declare a non-default `consentModel`.

Compliance logger additions are not subject to this consent threshold. They follow §7.8.2: the regulated member's own user agent commits the logger's Add unilaterally, not a remote admin, and the logger's presence is disclosed to all members (§7.8.4), not consented to.

### 4.6.2 DM Group vs. Private Channel

A DM group and a private Space channel (§4.4) are structurally similar: both are MLS groups with a restricted membership set. The distinction is:

- A private channel is owned by a Space, appears in that Space's state document (for authorized members), and is subject to the Space's compliance logging configuration.
- A DM group is owned by its members collectively, has no Space parent, and is subject to compliance logging only through the per-member obligation in §7.8.

Users who need a persistent, named, multi-party private conversation with Space-level administration (roles, moderation, compliance) SHOULD use a private Space channel rather than a DM group.
